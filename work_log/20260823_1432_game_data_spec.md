# Game data, covers and their API

**Goal: decide whether to mimic EmulationStation for game data and cover art,
then specify what the app does instead.**

## Result

**Take EmulationStation's media-role vocabulary. Reject its data model.**

Written to [`app/GAME_DATA.md`](../app/GAME_DATA.md). The types and resolvers
are implemented and tested in `app/shell`.

## What decided it

**ES identifies a game by its file path.** Move or rename a dump and the
metadata, art, cheats and per-game overrides are orphaned.

**The fleet already rejected that, three times, without coordinating:**

| Fork | Keys per-game content by |
| --- | --- |
| Vita3K | `TITLEID` |
| ARMSX2 | disc serial |
| xenia | 8-hex-digit title id |

Three forks, three consoles, one answer. **ES is the outlier, not this
project.** That settled the largest decision before any design started.

The second ES problem is `gamelist.xml` parsed at startup, which stalls the
first frame and contradicts the cheap-UI rule.

## What was kept from ES

- **Named media roles.** `cover`, `logo`, `screenshot`, `banner`. The UI binds
  to a role, so any art satisfying it works.
- **A short, boring metadata vocabulary.**

**Dropped: the video role.** A video snap is a per-frame decode and a
full-screen fill behind a menu. It is the most expensive thing an ES theme does.

## What was built

`app/shell/.../GameData.kt`:

- `GameKey(system, titleId)` — the identity. `storageId` normalises it to a
  filename-safe form once, so no caller invents its own scheme.
- `DumpId(contentHash)` — *which copy*, kept separate. A cheat targets a title;
  a code patch targets a build. That is the binding problem Cemu, rpcsx and eden
  each solved alone.
- `MetaSource` / `MetaField` / `MetaLayer` / `MetadataResolver` — four layers,
  user over scraped over bundled over derived, resolved **per field**.
- `MediaRole`, `MediaRequest`, `MediaStore`.

**The metadata resolver is the settings resolver again, deliberately.** Same
sparse-override rule, same precedence order. Correcting a wrong title must not
discard the scraped release date.

**Art is requested at a display size, not as a path.** A path-based API cannot
express this; it returns a file and the caller scales per frame.

## The shell no longer keys anything on a title

`Game` carried `title: String` as its identity and the library list used it as
its `LazyColumn` key. **That was the ES mistake in miniature.**

Now `Game` carries a `GameKey`, its `title` is a resolved metadata value, and
the list is keyed by `storageId`.

## Measured

- **56 tests pass**, up from 34. `GameDataTest` adds 22.
- `assembleDebug` succeeds.
- **No fork was touched.** All changes are inside this repo.

## A test that was wrong, and what it exposed

`near-identical sizes share one decode` failed. The cause was the test, not the
code: it compared 96 px and 97 px, which straddle a 32 px bucket edge.

**Bucketing narrows the window, it does not close it.** The fix kept an honest
test for the boundary rather than picking a pair that hides it. Closing the
window completely means snapping sizes at layout, which is a larger change than
the problem justifies now.

## Not done

- No index database, no media store implementation, no scraper, no on-disk
  format.
- **No sizes measured.** "Decode once at display size" is a rule with no number
  behind it. The number needs the device, and the device is in use.
- **Where scraped data comes from is undecided.** ScreenScraper and TheGamesDB
  have their own terms. **Check the licence before shipping a scraper**, the
  same gate as cheat databases.

## Not committed

Held, per the standing instruction: no commit until the core style is settled.

# Addendum, 14:58 — the cover UI

**Goal: draw covers in the library.**

## Built

| Where | Slot |
| --- | --- |
| Library row | 34 x 46 dp thumbnail |
| Metadata panel | 132 x 180 dp |
| Detail screen | 116 x 158 dp |

**Three sizes is three cache entries, deliberately.** The large cover must not
be an upscaled list thumbnail.

`MediaCache.kt` holds `CoverArt`, a bounded LRU `InMemoryMediaStore`, and the
`MediaSource` it decodes through. `Cover.kt` draws the slot. The store is owned
at the app root, not conjured by a CompositionLocal default, so there is one
cache and one memory budget.

## What drawing it forced, that the specification had not said

- **The pixel size is derived from `Dp` and the density, not measured.**
  Measuring means a zero-size pass, a decode, then a recomposition, per row, per
  scroll.
- **`CoverArt` stores a hue, not a colour.** A resolved colour would be wrong
  the moment the theme switches, and correcting it would mean throwing away the
  whole cache. **The cache now survives a theme switch.**
- **The slot is fixed; art fits inside it.** Box art aspect differs per system.
  Letting it set row height is what makes a lazy list expensive.
- **No crossfade when art arrives.** Per-row animation is per-frame work for a
  cosmetic transition, and a scroll would run dozens at once.

**This is the "the shell defines the contract" rule working as intended.** Four
decisions came out of drawing the screen, not out of arguing about the API.

## Measured

- **70 tests pass**, up from 56. `MediaCacheTest` adds 14.
- `assembleDebug` succeeds.
- **No fork touched. No device used** — another agent has the Thor.

## The tests are the point

"Cover art is decoded once at display size" is a rule in CLAUDE.md that **no
review can enforce**, because the failure is invisible until somebody profiles a
scroll on hardware. A counted decoder makes it a test:

- 50 re-appearances of one row decode **once**
- the thumbnail and the panel cover decode **twice**, correctly
- a game with no art **never reaches the decoder**
- eviction is least-recently-used, so scrolling back and forth keeps what is on
  screen

## Not done

- **Real image decoding.** The store is real; what it decodes is a placeholder
  colour chip with the title initials.
- **No scraper, no on-disk art format.**
- **No number for the decode cost.** The rule has a test, not a measurement.
  The measurement needs the device.
