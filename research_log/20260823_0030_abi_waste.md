# Most forks build ABIs the Thor cannot run, and it is measurable

**Goal: understand where a clean build's time actually goes, after measuring
one.**

Session 2026-08-23 00:30. Found while building Vita3K, confirmed against the
melonDS build measured the same night.

**Result: melonDS's 15 min 27 s clean build compiled its native code three
times. The Thor can run one of them.**

---

## The measurement

melonDS's build log, from the run timed at 15 min 27 s:

```
buildCMakeRelWithDebInfo[arm64-v8a]
buildCMakeRelWithDebInfo[armeabi-v7a]
buildCMakeRelWithDebInfo[x86_64]
```

And the merged native libraries in the APK:

```
arm64-v8a   armeabi-v7a   x86   x86_64
```

**Four ABI folders shipped. One is usable.** The Thor reports `arm64-v8a`.

**Native compilation is per-ABI**, so roughly two thirds of the C++ work in that
15 minutes produced code the target device cannot execute — and it is carried in
the 55.5 MB APK afterwards.

## The fleet

App module `abiFilters`, read from each fork's own app build file rather than
from a vendored sample.

| Fork | ABIs built | Usable on the Thor |
| --- | --- | --- |
| **ARMSX2** | `arm64-v8a` | **1 of 1** |
| **eden** | `arm64-v8a` | **1 of 1** |
| Vita3K | `arm64-v8a`, `x86_64` | 1 of 2 |
| xenia | `arm64-v8a`, `x86_64` | 1 of 2 |
| GameThor | `arm64-v8a`, `armeabi-v7a` | 1 of 2 |
| **melonDS** | `armeabi-v7a`, `arm64-v8a`, `x86_64` | **1 of 3** |
| **azahar** | `arm64-v8a` | **1 of 1** |
| **rpcsx** | `arm64-v8a` **by default** | **1 of 1** |
| **Cemu** | `arm64-v8a` | **1 of 1** |

**Four forks already do the right thing**, not two. ARMSX2, eden, azahar and
rpcsx build `arm64-v8a` alone.

### rpcsx already measured this, and its numbers are better than my estimate

Resolving `rpcsxAndroidAbis` found the whole analysis written into
`app/build.gradle.kts`:

> This fork targets the AYN Thor, which is arm64-v8a. Building x86_64 as well
> put **26 MiB compressed / 65 MiB uncompressed of unreachable code into a
> 96 MiB APK, more than half the payload, and doubled the native compile.**
> Anyone who needs it back can pass `-PrpcsxAndroidAbis=arm64-v8a,x86_64` or set
> `RPCSX_ANDROID_ABIS`; the arm64-only default is what ships to the device.

**"Doubled the native compile" is the bound this log called unknown.** For a
two-ABI fork the native saving is about half; melonDS builds three.

**And it keeps the escape hatch as a property rather than deleting the
capability**, which is the right shape: the default serves the device, and the
override serves whoever needs it.

**The irony is worth recording.** rpcsx is the fork that is **out of the app** on
licence grounds, and it has the best-documented build decision in the fleet.
**Being excluded from the binary did not stop it being the reference for how to
write this down.**

### So my framing two commits ago was too broad

I wrote that "most forks build ABIs the Thor cannot run". **Half do. Four are
already correct, and one of those measured it.** The five that are not are
Vita3K, xenia, GameThor, Cemu and melonDS.

**The finding survives; the emphasis was wrong.** It is not a fleet-wide
oversight, it is a fix that four forks made independently and five have not.

**CORRECTED 2026-08-23 by reading the actual line.** Final tally: **five forks
build `arm64-v8a` alone** — ARMSX2, eden, azahar, rpcsx and **Cemu**. **Four
build ABIs the device cannot run** — Vita3K, xenia and GameThor build two,
melonDS builds three.

**Cemu was recorded as a failure and it is not.** Its build file carries a
disabled line directly above the live one:

```kotlin
// abiFilters("arm64-v8a", "x86_64")
   abiFilters("arm64-v8a")
```

**The lint took the first match and did not skip comments.** Cemu's own
`AGENTS.md` states it correctly — *"The app currently builds ARM64 only"* — and
was disbelieved because a tool disagreed with it.

**The rule that comes out of this is not "trust the docs".** It is: **when a
tool and a document disagree, read the actual line.** Today the document was
right; earlier today, twice, the document was wrong. Neither is a reliable
default and the line always is.

## Why this is not just tidiness

`CLAUDE.md`'s standard row already says it: *"Drop `armeabi-v7a` and `x86_64`
from the shipping build. The Thor is arm64."* **That was written as a
correctness rule. It is also the largest single lever on build time nobody had
priced.**

It touches three decisions at once:

1. **Phase 0.3.** Every clean-build number gathered from now on is inflated by
   whatever ABIs that fork happens to build. **Record the ABI list beside the
   time, or the numbers are not comparable across forks.**
2. **The build location decision.** It asks how much an agent can do
   unattended. **Cutting melonDS to one ABI attacks the dominant remaining cost
   after `librashader`**, and unlike a CI migration it is a one-line change.
3. **The packed binary.** `CLAUDE.md` accepts "a large binary" as a stated cost
   of packing seven backends together. **Part of that size is ABIs the device
   cannot run**, which is a cost being accepted without being examined.

## The obvious experiment, not yet run

**Rebuild melonDS clean with `abiFilters` set to `arm64-v8a` alone and compare.**

**Prediction: a large cut to the native portion and little change to the rest.**
The `librashader` Rust build is a host-side dependency graph and should be
roughly unchanged, so the saving is bounded by however much of the 15 minutes is
native C++ rather than Rust and Kotlin.

**That bound is the interesting number and it is unknown.** The Rust phase
dominated the log by volume, so the saving could be modest. **Do not promise a
two-thirds reduction; measure it.**

## Method note

**This was found while a different fork failed to build**, not by looking for
it. The Vita3K build log showed `configureCMakeRelWithDebInfo[x86_64]` scrolling
past on a device target that has no x86, which prompted checking melonDS's log
for the same thing.

**A build log is evidence, and reading one you did not intend to read is
cheap.**
