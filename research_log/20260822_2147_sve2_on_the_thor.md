# Does the AYN Thor have SVE2?

**Goal: decide whether the Snapdragon 8 Gen 2 has SVE2, and whether a flag can
reach it, because `THOR_TARGET.md` was written on the claim that it has none.**

Session 2026-08-22 21:47. Triggered by a challenge to the north star: that
Whatcookie said something about the Odin or the Thor having SVE2 behind a flag.

**Verdict: the challenge is half right, and the half it is right about matters.
The decision does not change.**

---

## The short answer

| Question | Answer | Confidence |
| --- | --- | --- |
| Does the Cortex-X3 IP implement SVE2? | **Yes** | high, ARM's own documentation |
| Does the shipped SM8550 expose SVE2? | **No** | high, measured on this device |
| Can a compiler flag reach it? | **No** | high |
| Can anything reach it? | **Unknown.** Silicon or kernel, undetermined | **open** |
| Would it be a throughput win if reached? | **No. 128-bit, same as NEON** | high |

**The operative fact is unchanged: this device traps SVE instructions, so do
not target `armv9-a`.** If anything the finding strengthens that warning.

Five other fork documents agree on the observable, from three separate

```
asimddp  i8mm  bf16  fphp  asimdhp  atomics  lrcpc  ilrcpc  sha3
```

No `sve`. No `sve2`. azahar's LLVM configuration line confirms the fleet acts on
it: `attrs=+sha3,+dotprod,+i8mm,-sve,-sve2`.

## The IP does implement SVE2

From ARM's own product documentation:

- **Cortex-A510**: "designed to fully support the Armv9.0 ISA including the
  Scalable Vector Extension (SVE) and SVE2. **Regardless of the vector unit size
  or configuration, for SVE, there is a 128b vector register file.**"
- **Cortex-A710**: "the SVE2 engine is 128-bits wide, similar to the Cortex-X2."

So the cores in this SoC are built with SVE2. **The hardware claim in the
challenge is correct.**

---

## The shipped SoC does not expose it

Multiple independent sources state that Qualcomm disabled SVE across this
generation of Snapdragon parts. It is consistent with the measurement.

Two further data points that frame it:

- **Oryon, in the Snapdragon 8 Elite and X Elite, does not support SVE or SVE2
  either.** It implements ARMv8.7 and uses NEON.
- **Oryon Gen 3, in the Snapdragon X2 Elite, adds SVE and SVE2.** So Qualcomm is
  only now adopting it, which is evidence the earlier omission was deliberate
  rather than accidental.

---

## Can a flag reach it? No, and here is the mechanism

**There is no compiler flag, app setting or userspace toggle that enables SVE.**
Compiler flags select which instructions to emit. They cannot make a trapping
instruction execute.

Exposure is decided by the kernel:

- SVE is reported to userspace through `HWCAP_SVE` in the aux vector, and shows
  in `/proc/cpuinfo` as `sve`.
- **If the kernel is built without `CONFIG_ARM64_SVE`, the hwcap is not reported
  even when the hardware supports SVE.**
- Without kernel support there is no SVE register state save and restore across
  context switches, so executing SVE would be unsafe as well as untrapped.

So "needs a flag" is true only in the sense of a **kernel build option**, not a
build flag for our app. Reaching it would require a custom kernel and root, on a
device that must also still boot Android.

## The open question, and the test that closes it

**Undetermined: whether SM8550 has SVE fused off in silicon, or merely hidden by
the vendor kernel.**

This matters only for accuracy, not for the plan. Both cases give the same
answer today.

**Read this on the device to close it:**

1. `zcat /proc/config.gz | grep -i ARM64_SVE` — is `CONFIG_ARM64_SVE` set?
2. Read `ID_AA64PFR0_EL1.SVE`. Non-zero means the silicon implements it.

Interpretation:

| `CONFIG_ARM64_SVE` | `sve` in cpuinfo | Conclusion |
| --- | --- | --- |
| set | absent | **fused off in silicon.** Nothing can reach it |
| not set | absent | **kernel choice.** A custom kernel could expose it |

Corroborating evidence available without the Thor: SM8550 has had mainline Linux
support since Linux 6.3, and mainline `arm64` defconfig enables
`CONFIG_ARM64_SVE`. **A mainline Linux `/proc/cpuinfo` from any SM8550 device
answers the question.** The Odin 2 is the same SoC and runs Linux, so that
report may already exist.

---

## Why it would not be a win anyway

**Every ARMv9 core in this SoC implements SVE at 128-bit vector length.** That
is the same width as NEON, and 128 bits is the minimum an SVE vector can be.

So SVE2 here would offer **no throughput advantage**. The gain would come only
from SVE2's instruction semantics — predication, gather and scatter, bitperm,
and the vector-length-agnostic forms — against extra register pressure and a
second code path to test.

Whatcookie's own post makes the same observation about a related extension:

> "SVE2.1 adds properly vector length agnostic versions of these instructions,
> for instance TBLQ or DUPQ. **The ironic thing is that today, the only machines
> with SVE2.1 support only have 128b SVE.**"

**That is the same disappointment, one extension along.** It is also why the
rpcs3 SVE2 work was never the interesting part of that project for us: the
transferable wins were `SDOT` and `UDOT`, `EOR3` and `BCAX`, the spin-wait fix
and the target-feature detection fix, all of which this device does have.
