# ADPF surveyed: melonDS has the only complete implementation, four forks have none

**Goal: survey Android Dynamic Performance Framework support across the fleet.
`CLAUDE.md` records it as unsurveyed.**

**On a handheld with a thermal budget, telling the OS what frame time you are
aiming for is the difference between the scheduler guessing and the scheduler
knowing. This is [Foundation](../CLAUDE.md) point 2 territory and it was
unmeasured.**

## Method

Counted files using the four real ADPF entry points, per fork, excluding vendored
trees. **Counting the word "thermal" is useless** — every fork mentions it. The
APIs are the measurement.

| --- | --- | --- | --- | --- |
| **melonDS** | **12** | 0 | **1** | **9** |
| ARMSX2 | 5 | 0 | 0 | 1 |
| Cemu | 4 | 0 | 0 | 1 |
| **xenia** | 2 | **1** | 0 | 1 |
| **rpcsx** | 1 | **1** | 0 | 1 |

| **GameThor** | **0** | 0 | 0 | 0 |

**Four of nine forks have no ADPF at all**, including the two largest Android
frontends after melonDS.

**Only xenia and rpcsx read `getThermalHeadroom`**, which is the API that says
how close the device is to throttling. **Everything else is open loop.**

## melonDS's implementation, and it is the one to take

**Ten files under `app/src/main/cpp/performancehint/`**, with a three-tier
abstraction chosen by a factory:

```cpp
if (apiLevel >= 33)      return std::make_unique<NdkPerformanceHintManager>();
else if (apiLevel >= 31) return std::make_unique<JniPerformanceHintManager>(jniEnvHandler);
else                     return std::make_unique<DummyPerformanceHintManager>();
```

**Four things worth taking:**

1. **A real interface with a no-op tier.** `DummyPerformanceHintManager` means
   call sites never branch on availability. **That is the pattern this project
   wants everywhere** — the availability test lives in one place.
2. **NDK first, JNI as the fallback.** The C API exists from API 33; before that
   only `android.os.PerformanceHintManager` through JNI. The JNI path is 100
   lines of `FindClass` and `GetMethodID` with **exception clearing and local-ref
   deletion on every failure path**, which is the part nobody writes correctly
   the first time.
3. **The API level is a parameter.** `create(jniEnvHandler, apiLevel)` exists
   beside `create(jniEnvHandler)`. **That makes the tier decision unit-testable
   without a device**, which is exactly this project's own discipline.
4. **`ThreadSafePerformanceHintSession`.** A hint session is not thread-safe, and
   an emulator reports work duration from more than one thread. **melonDS is the
   only fork that hit this problem, because it is the only one reporting from
   nine sites.**

## What this project should do with it

**Take the NDK tier and delete the other two.**

**The Thor is API 33**, so `apiLevel >= 33` is a constant here. The JNI tier and
the Dummy tier exist to serve devices this project does not have. **That is the
DELETE operation from `CLAUDE.md`'s table**, and this is a clean small example of
it: the shared version is smaller than melonDS's, not a merge of it.

**Keep the thread-safe session and the interface.** Those serve a real property —
more than one reporting thread — not device variability.

**Add `getThermalHeadroom`, which almost nobody uses.** Reporting work duration
is open loop; reading headroom closes it. **xenia and rpcsx each read it in one
file**, so the technique exists in the fleet to copy.

## The caution this repo has earned

**`CLAUDE.md` already says: measure without ADPF first, or the hint is tuned
against an unknown baseline.** That still holds. **This survey says who has the
mechanism. It does not say the mechanism helps.**

**And ADPF is currently disabled on this device by persisted config**, so any
before-and-after must state that setting.

## Limits

- **File counts, not call-site counts.** A fork with one file may call it many
  times.
- **melonDS's call sites were not read**, only counted. **Whether its nine
  `reportActualWorkDuration` sites report sensible durations is unknown.**
- **No claim that the four zero forks cannot do this**, only that they do not.
- **Nothing is measured**, and no frame or thermal number is attached to any of
  this.
- **melonDS's `-mtune=cortex-x3` and its lack of thread affinity are recorded
  elsewhere in `CLAUDE.md`.** Together with this, melonDS looks like the most
  Android-native fork in the fleet and the one that never asks for a specific
  core. **Those two facts sit oddly together and neither has been measured.**
