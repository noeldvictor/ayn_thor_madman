# Read the swizzle code. PMULL is dead, and the better technique is already here.

**Goal: read one fork's texture swizzle code before proposing carryless multiply
for it, as [`DEVICE_QUEUE.md`](../DEVICE_QUEUE.md) entry 14 requires.**

No device. No build. **The question closes on reading alone.**

## Result

**The `PMULL` candidate is dead. Two forks already solve this better, by two
different methods, and both are in the fleet.**

| Fork | How it untiles | NEON in the texture path | Structured `LD2`/`3`/`4` |
| --- | --- | --- | --- |
| **xenia** | **GPU compute shaders** — 171 `texture_load_*_cs` files | n/a | n/a |
| **azahar** | **CPU, heavily vectorised** | **83** | **27** |
| melonDS | CPU | 7 | 2 |
| ARMSX2 | CPU | 8 | 0 |
| Cemu | CPU | 2 | **0** |
| **Vita3K** | CPU | **0** | **0** |

## Why PMULL loses, in two independent ways

### 1. The per-pixel address is a lookup table

azahar's core interleave, in `src/video_core/utils.h`:

```cpp
static constexpr u32 MortonInterleave(u32 x, u32 y) {
    constexpr u32 xlut[] = {0x00, 0x01, 0x04, 0x05, 0x10, 0x11, 0x14, 0x15};
    constexpr u32 ylut[] = {0x00, 0x02, 0x08, 0x0a, 0x20, 0x22, 0x28, 0x2a};
    return xlut[x % 8] + ylut[y % 8];
}
```

**Two 8-entry tables, `constexpr`, two L1 loads and an add.**

**A carryless multiply cannot beat that.** It needs the operands moved into a
vector register, `PMULL`, and the result moved back — **and cross-file transfers
are exactly what the A710 stalls three cycles on** when a quad-word source was
assembled from single words, which `CLAUDE.md` already records.

### 2. The bulk path uses a better instruction than PMULL

**azahar does not compute per-pixel addresses in the hot path at all.** It moves
whole tiles with NEON, in `MortonCopyTile32A64`:

```cpp
const uint64x2x2_t left = vld2q_u64(...);
```

**`vld2q_u64` is ARM's structured load `LD2`, and it de-interleaves as it
loads.** The hardware performs the de-interleave **as part of the memory
operation**, before the data is ever in a register.

**That is strictly better than `PMULL`**, which can only act on data already
loaded. And for the byte-order fixups azahar uses **`vqtbl1q_u8`** — a `TBL`
permute — with a 16-entry index table.

> **The interleave problem is solved by the load unit, not the multiplier.**

## What this says about the original question

**The observation that emulators use hardware in clever ways is correct. The
clever uses in this fleet are structural, not instruction substitutions.**

**Three different solutions to one problem, all already written:**

| Method | Fork | What it exploits |
| --- | --- | --- |
| **Move the work to the GPU** | xenia | compute shaders, one invocation per block |
| **De-interleave in the load** | azahar | `LD2` structured loads |
| **Permute in one instruction** | azahar, xenia | `TBL` / `TBX` |

**None of them is a repurposed crypto instruction.** The two crypto-style
attempts in this fleet — `EOR3`/`BCAX` fusion and the `TBL2`-for-`TBX2` rewrite —
**both measured null.**

## The real opportunity, and it is a PROPAGATE

**Vita3K has zero NEON in its texture path. Cemu has two.**

**The PS Vita stores textures swizzled**, so Vita3K is doing Morton
de-interleaving in scalar code while **azahar's `LD2` and `TBL` technique sits in
the same fleet**, written, working, and GPL-2.0-or-later.

**That is the fourth time today a fix was already in the fleet and unrecorded**,
after frame generation, storage aggregation and haptics.

**Do not treat this as proven yet.** What is measured is **the presence of
intrinsics**, not that Vita3K's swizzle is hot, nor that its textures are large
enough for a vectorised copy to pay. **Read Vita3K's path before proposing the
port** — the same rule that killed `PMULL`.

## Entry 14 is closed

`DEVICE_QUEUE.md` entry 14 predicted three outcomes and said two of them would
close the question with no device. **The outcome was "already hand-vectorised",
which was one of them.**

**The read cost about twenty minutes and saved a device run and a patch.**

## What was not read

- **Cemu, ARMSX2 and melonDS swizzle paths.** Their NEON counts are greps.
- **Whether Vita3K's swizzle is hot at all.** No profile.
- **xenia's shader tiling math was skimmed, not verified** — `XenosTextureTiledAddress2D/3D`
  and an XOR-based macro-tile swizzle, read from the shader source only.
